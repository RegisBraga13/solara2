# Rastreamento técnico público — solara.doctor

**Data:** 22/10/2026 (America/Fortaleza)  
**Objetivo:** obter evidência verificável para [`instructions.md`](../instructions.md) sem depender de afirmações comerciais.  
**Método:** requisições HTTP de leitura para páginas públicas, `robots.txt`, sitemap, manifesto PWA, HTML, CSS e bundles JavaScript referenciados pelo HTML. Extração de links, metadados e chamadas estáticas. Nenhum login, mutação, tentativa de contornar autorização ou coleta de dados de pacientes.

## Limites e política do rastreamento

O [`robots.txt`](https://solara.doctor/robots.txt) declara `Disallow` para `/api/`, `/app/`, `/pair/`, `/record/`, `/m/`, `/login`, `/signup` e `/onboarding`. O rastreamento automatizado de conteúdo se concentrou no sitemap, página pública e assets estáticos. Foram feitas leituras pontuais de HTML de login/onboarding para entender o fluxo de entrada; não houve crawl de área protegida ou API. O link `/app` sem cookie redireciona para `/login?redirect=%2Fapp`. A captura autenticada fornecida pelo usuário é a única evidência direta da tela interna.

**Níveis de certeza:** **confirmado no HTML/CSS**; **presente em código cliente público** (a execução real depende de autenticação/servidor); **inferência** (hipótese que requer teste autorizado). A existência de código no bundle não prova disponibilidade da função em produção.

**Limite técnico da alegação de vídeo:** a [arquitetura de segurança WebRTC (RFC 8827)](https://www.rfc-editor.org/rfc/rfc8827.html) estabelece DTLS-SRTP para proteger mídia. O [SFrame (RFC 9605)](https://www.rfc-editor.org/rfc/rfc9605.html) distingue criptografia entre participante e servidor de mídia da criptografia de conteúdo entre participantes. Sem topologia, código de mídia, gestão de chaves e fluxo de gravação, a captura não comprova E2EE real nem descarte do áudio.

## Análise estática de bundles públicos

Os bundles abaixo foram referenciados pelo próprio HTML público. Os achados são **presença de código no cliente**, não captura de tráfego de uma sessão autenticada.

| Bundle | Achado verificável |
|---|---|
| [`app/login/page`](https://solara.doctor/_next/static/chunks/app/login/page-1215eba7ec493643.js) | Chama `auth.signInWithPassword({email,password})`; após sucesso navega ao destino `redirect`. O clique em “Esqueci minha senha” apenas mostra o aviso “Recuperação de senha em breve”. |
| [`app/onboarding/page`](https://solara.doctor/_next/static/chunks/app/onboarding/page-e7986c9211418b6f.js) | Fluxo de telas `profession → account → lgpd → wizard → done`; wizard tem **Boas-vindas, Experimente, Perfil, Recursos, Tudo pronto**. Há perfis `doctor`, `psychologist`, `nutritionist`, com cores e vocabulário próprios. |
| Mesmo bundle de onboarding | Chama `auth.signUp` com e-mail, senha e metadados `full_name`, registro profissional formatado, `profession`, `subspecialty`, `onboarding:true`. Após sessão imediata, tenta `POST /api/onboarding/complete`. Não foi feita requisição a essa API; payload e resposta do servidor são desconhecidos. |
| Bundles compartilhados de autenticação | Incluem biblioteca Supabase; o código de login/onboarding instancia cliente com URL de projeto Supabase. Isso confirma uso de Supabase no fluxo de autenticação cliente, não prova que todos os dados clínicos ficam no Supabase. |

**Detalhe do registro profissional no cliente:** médicos usam formato `CRM/UF número`; psicólogos usam `CRP região/número`; nutricionistas usam `CRN-região número`. É formatação exibida/enviada pelo cliente, não validação automática do conselho. O estado inicial do formulário contém `plan:"pro"`; sem execução autorizada não se pode concluir que há contratação ou cobrança nessa etapa.

**Observação de segurança:** metadados enviados no `signUp` são entrada do usuário. Qualquer decisão de autorização, validação profissional ou acesso clínico precisa de confirmação e armazenamento confiável no servidor. Não interpretar `onboarding:true`, profissão ou CRM enviado pelo cliente como prova de credenciamento.

## O que o crawl não revela

- DOM, URLs, tráfego e estados das abas internas após login.
- Rotas e schemas da API clínica, webhooks, storage de áudio, provedores de IA/pagamento/assinatura.
- Políticas RLS, localização dos dados, retenção efetiva, segurança de sessão ou conformidade certificada.
- Funcionamento real do modo offline, prazo de exclusão do áudio, limites de uso e disponibilidade dos tipos de documento.

**Próxima medição necessária:** aba autenticada compartilhada via ferramenta de navegador ou capturas de cada fluxo com dados sintéticos. Registrar URLs, controles, estados de erro e sucesso e, se houver autorização e ferramenta adequada, tráfego de rede da própria sessão de teste. Não usar cookie, token ou senha exportados para contornar a separação da sessão.
